# Story 1.2: Create MiniRAGAgent.py wrapper class

## Status
Draft

## Story
**As a** Developer,
**I want** to implement the `MiniRAGAgent` class,
**so that** we can use MiniRAG as a drop-in replacement for the baseline RAG system in the evaluation pipeline.

## Acceptance Criteria
1. `MiniRAGAgent` class exists in `src/agents/MiniRAGAgent.py`.
2. `MiniRAGAgent` implements `answer(instance: LongMemEvalInstance) -> str`.
3. `__init__` accepts `model_name` and `embedding_model_name` (compatible with `config/config.py`).
4. Data Adapter correctly converts `LongMemEvalInstance` sessions into MiniRAG's expected input format.
5. `answer` method triggers indexing of the converted data and queries MiniRAG for the answer.
6. System supports configuration of the specific models (LLM and Embedding) passed in initialization.
7. `answer` return value is compatible with `JudgeAgent` evaluation logic.

## Dev Notes
- **Source Tree Location**: `src/agents/MiniRAGAgent.py` [Source: docs/architecture.md#Source Tree]
- **Interface Definition**: `MiniRAGAgent` must have `answer(instance: LongMemEvalInstance)` method. [Source: docs/architecture.md#Component Architecture]
- **Instantiation Contract**: `main.py` instantiates this agent as `MiniRAGAgent(model_name=..., embedding_model_name=...)`. This differs from `RAGAgent` which takes a `LiteLLMModel` object. [Source: main.py#L79-L81]
- **Data Model**:
    - **Formal Definition**: The benchmark instance is a 3-tuple $(S, q, a)$.
        - $S$: Sequence of sessions $[(t_1, S_1), ..., (t_N, S_N)]$. Mapped to `LongMemEvalInstance.sessions`.
        - $q$: Question. Mapped to `LongMemEvalInstance.question`.
        - $a$: Answer. Mapped to `LongMemEvalInstance.answer`.
    - **Structure**:
        - `LongMemEvalInstance.sessions` is a list of `Session` objects.
        - `Session.messages` ($S_i$) corresponds to `haystack_sessions` in the raw JSON.
        - **CRITICAL**: The `haystack_sessions` field in `data/longmemeval/longmemeval_s_cleaned.json` is a `List[List[Dict]]`.
            - Format: `[[{"role": "user", "content": "..."}, ...], [{"role": "user", "content": "..."}, ...]]`
    - The adapter MUST flatten or process these sessions into a format MiniRAG can index (likely text blocks or documents).
    - Verify mappings: `haystack_session_ids` -> `Session.session_id`, `haystack_dates` -> `Session.date`. [Source: src/datasets/LongMemEvalDataset.py & benchmark_explanation.md]
- **Dependencies**: Use `minirag` package installed in Story 1.1.
- **Evaluation Flow**:
    - `MiniRAGAgent` is part of a pipeline: `main.py` -> `MiniRAGAgent.answer` -> `JudgeAgent.judge`.
    - `JudgeAgent` will use **Gemini 1.5 Flash** (to be configured in `config.py`/`main.py`). The `MiniRAGAgent` must just return the answer string to facilitate this.
    - Result saving is handled by `main.py` in `data/results`. `MiniRAGAgent` does not save results itself. [Source: main.py#L88]
- **Configuration**:
    - Agent switching is controlled by `config.py` (`agent_type="minirag"`).
    - `main.py` uses this config to instantiate the agent.
    - Ensure `MiniRAGAgent` instantiation in `main.py` matches the class definition.

### Testing
- **Test File Location**: `tests/test_minirag_agent.py`
- **Test Standards**: Unit test should verify the adapter logic and the integration flow (mocking MiniRAG internals if necessary, or running a functional test).
